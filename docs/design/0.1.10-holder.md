# 0.1.10 design: which process holds which session, on which login

Rows: T56 (G1.19), T47 (G1.16), T57 (G2.51), T54 (G1.17); T27 (G3.14) is not joined (section 4).
Status: plan only. Reviewed (GO, 3 changes, folded in below). Code starts after the 0.1.9 release passes its real-machine round and the department head says go.
Base: 9540296 (the 0.1.9 candidate), read on 2026-11-23.

## The question, and what is wrong with today's answer

On every pass (record, census, and revive's check right before each start), Tardigrade asks this about each
session on the record: is it running, in which process, and on which login? Today three functions answer it
separately: `live()`, `running_sids()` and `holder_text()`. Each re-reads every process from scratch, and each
treats a failed read of one process as "nothing there":

- `env_facts()` returns empty facts when the environment read fails. On a Mac, `ps eww` is one spawn per
  process, its exit code is not checked, and the 30 s timeout gives `""`. The record then writes the empty
  account. **That is the lead for T57.**
- An empty config folder also points `session_json()` at the wrong `sessions/` folder. The session then
  looks not running, and it goes on the down list (the same harm as T54).
- A process is counted as a Claude by its name first. An npm install up to 2.1.112 runs under `node`, then
  renames itself `claude` and drops `--resume`. Until its session file is written, it is invisible (T56).

**Design:** one read per pass gives one table of holders. Each recorded session gets one of three verdicts:
**held**, **not held** or **cannot tell**. Each fact in the table carries where it came from.

## 1. The read (T47)

- **Linux:** scan `/proc/<pid>/stat` directly; the owner comes from the entry itself. The list gives pid,
  parent pid, uid, name, start time (field 22) and tty (field 7).
- **macOS:** one `sysctl` call, `KERN_PROC_ALL`, through ctypes. This is already used for the arguments, so it
  is no new dependency. It returns `kinfo_proc` for every process: pid, parent pid, uid, name, start time and
  tty, with no spawn. `ps` stays as the fallback, and its exit code is checked.
- **If the list read fails:** everything is "cannot tell", as in 0.1.9 (T52, T53 and T55 are unchanged).
- **Candidates:** this user's processes named `claude` or a version (`2.1.330`), plus this user's `node` and
  `bun` processes whose script argument ends in `claude-code/cli.js` (the old npm phase).
- **What is read of whom:** only candidates have their arguments, environment, folder and session file read.
  Nothing more is read of any other process. A process in a `skip_cwd_prefix` folder has only its folder read,
  as today.

## 2. How a holder is recognised, in order (the first sign that answers wins)

1. **The same process as last pass.** The row's `holder` (pid, start time and boot id, a new field) matches a
   live process. Then it is the same session, even if its session file cannot be read now. A holder from an
   earlier boot never matches: after a reboot, start times are small and pids are reused, so the pair alone
   can repeat.
2. **Its session file.** `sessions/<pid>.json` is readable and names the session id, and its `startedAt` is not
   earlier than the process's own start (2 s slack). A file older than the process was left by a reused pid,
   so it is ignored. The file is looked for in the config folder from the process's environment. If that
   environment was not read, every config folder the record knows of is tried.
3. **Its arguments.** This covers every install before the file is written, and the npm `node` phase before
   the rename.
   - `--resume <id>` or `--session-id <id>`: it holds that id.
   - `--continue` (`-c`): it holds that folder's latest conversation. That is the conversation file in the
     folder's project folder that was written last before the process started, so it names one id.
   - With `--fork-session`, the process starts a new id, so it holds no recorded session.
4. **What is left.** Each remaining process falls into one of two kinds:
   - **A new conversation:** its arguments are intact, and it has no resume, continue or session-id flag.
     It holds no recorded session and holds nothing back. Its own program says whether its arguments are
     intact: Linux `/proc/<pid>/exe`, macOS the exec path at the head of `KERN_PROCARGS2`. A native
     `claude` started bare shows exactly `["claude"]`, which is intact.
   - **An unidentified candidate:** it could be holding one recorded session. There are two cases:
     - its arguments are gone: the program is `node` (or `bun`) while its name is `claude`, which is the
       old npm install after its rename;
     - `--resume` with no id: the picker, where a person is choosing a session.

   Tardigrade knows each candidate's pid, start time and folder. **A candidate holds at most one session.**

If two live processes name one session id, census names both as two copies, and revive starts neither.

## 3. "Cannot tell"

- **For all sessions:** the list read failed. Behaviour is unchanged from 0.1.9: record skips the pass, census
  gives no count, and revive starts nothing and reads again every `retry_gap_s` for up to `retry_min`.
- **For one session, case a: K unidentified candidates in a folder with N recorded sessions to start.**
  Revive's own starts always carry `--resume <id>`, so they are never candidates. (The reviewer ruled on
  this case.)
  - **The wait:** that folder's sessions are started last in the run. A candidate usually names itself within
    seconds, once its session file is written. Then sign 2 or 3 settles it, and only the session it holds is
    left out.
  - **While any candidate in that folder is unidentified, all N sessions there are held.** Each start is
    preceded by a fresh read. The held sessions are looked at again each round, up to `retry_min` (25 min, no
    setting of its own). If a candidate is still unidentified then, all N are listed as "not started".
  - **Why all N, and not the newest K:** a second copy of a session is the one harm here that cannot be undone
    (P1, P10). Two copies both act on one conversation, and naming it afterwards changes nothing.
  - **What it costs:** on a shared Linux machine on Mon 2026-11-23, the record had 100 sessions in 97 folders. The one shared
    folder, the home folder, held 4. Holding all N strands at most those 4, for up to 25 minutes, and only
    while a candidate exists:
    - an old npm install past its rename, which none of the test machines has today;
    - or a person in the picker during a restore. They are choosing right then, and can wait, or run revive
      again after they pick.
  - **One rule:** it is easier to tell and to test than a guess about which session a person took.
  - **What the person is told:**
    - The log and the report say, for example: "FOLDER: 1 Claude process could not be told apart (pid N,
      since 7:02 AM, old install after its rename); held back all 3 sessions there until it can be told
      apart."
    - Census names every unidentified candidate at once, whatever its age, and the sessions it holds back.
    - **The person never waits in silence.** For as long as a folder's sessions are held for this reason,
      census and every revive round's log line say three things: which process holds them back (pid, and its
      tmux session or terminal when it has one), since when, and the one thing the person can do. For
      example: "3 sessions in ~ held back since 7:02 AM by a Claude process that cannot be told apart yet
      (pid 4242, tmux work:1). Answer or end that session; the next pass then starts the rest."
  - **This is the rule on every machine**, not only on the machine where it was measured.
- **For one session, case b:** a holder is found by sign 1 or 3, but its session file or its environment
  cannot be read. Its row is kept exactly as last written, with `unread_since` set. The log has one line when
  this starts and one when it ends, and census names it ("could not be read since 7:12 AM"). The rest of the
  record is written. One file that stays bad freezes nothing but its own row (T54).
- **What "cannot tell" never becomes:** "down", "not running", or a blanked field. A row that has been
  "cannot tell" for more than 24 h is named louder in census. It is never dropped silently.

## 4. The login a record carries forward (T57; built in 0.1.11; not joined with T27)

Rewritten 2026-11-24, after the cause was read. The sighting behind T57 was a person's own doing: three sessions
were ended and started again by hand on the machine's own login, on purpose, and the record followed what ran
without a line. So the first rule of this section ("another login than the row: hold the session") was wrong
for the real case: a session its owner moved must still come back after a restart. The maintainer's ruling:
split it by who started the running process.

**The environment read answers read or not read.**

- **Linux:** not read when `environ` cannot be opened, or holds no `KEY=value` pair.
- **macOS:** `ps eww`, not read when its exit code is not 0 or no `KEY=value` pair comes back. Seen on a clean
  test account (macOS 13.7.8, Claude Code 2.1.330, not logged in): 1,300 reads of seven Claude Code processes,
  0 failed and 0 without the label each was started with. A failed read was not seen by us.

**Who started the running process.** Tardigrade starts a session as `<shell> -ic '. <that session's start
file>'`, and Claude runs under that shell; when Claude ends, the start file replaces the shell with a plain login
shell. So a running Claude with that session's start file named on the command line of a process above it was
started by Tardigrade; any other was started by its owner. When a command line above it cannot be read, the
answer is "cannot tell". This comes from the process list a pass already takes; there is no new marker.

**The login facts** are the account label, the token fingerprint, the Claude Code folder and `carry_env`. They
are facts of a session's start, not of each pass.

| what the pass finds | what the row does | what is said |
| --- | --- | --- |
| environment not read | keeps its login facts, gains `env_unread_since` | one log line, the first pass |
| environment not read, and no row yet | nothing is written for it this pass | one log line |
| read, same login as the row | takes what was read, `env_read: true` | nothing |
| read, another login; started by its owner | follows what was read | one log line (was, now, since when); census names the change until the next restart |
| read, another login; started by Tardigrade | keeps what it had, gains `login_seen` | one log line; census names it and the start line's fault (the account command gave another login, or none) |
| read, another login; cannot tell who started it | keeps what it had, gains `login_seen` | one log line saying it cannot tell |
| read, another login; the row has no `env_read` (0.1.10.1 or older) | takes what was read | one log line |

- "Another login" is another account label, another token fingerprint, or another Claude Code folder. A
  session Tardigrade started always carries its row's label (the start file sets it), so for those it is the
  fingerprint or the folder.
- **A row with `login_seen` is started again from its row at the next revive, and checked again.** A token store
  that could not be reached at one boot must not strand a session for good. If it comes up on another login
  again, it is "needs you" again and nothing is typed into it, as before.
- **A person's word that what runs is right** (a renewed token, for example): `record --accept <session>`, for
  that session only, with one log line. `record --force` still takes what runs now for every session.
- **After a start, `same login?` with an environment that could not be read** is neither yes nor no: the session
  is "needs you" with words of its own, and nothing is typed.
- **Rows from 0.1.10.1 and earlier have no `env_read`.** Their first good read is taken as it is.

What is not built here: saying beforehand which running sessions are on a login the restore cannot give back
(T27, due 0.1.12). Noted for it, seen on Linux with tmux 3.4: a session made in a tmux server that is already
running gets the server's environment, not the caller's, unless `new-session -e` is used.

## 5. What it costs a machine with a hundred sessions

**Measured Mon 2026-11-23, 6:49 AM ET.**

| Machine | Read | Time |
|---|---|---|
| Linux: 1822 processes, 101 of this user's Claude processes, load 16 | today's `ps` list | 47 ms |
| | `/proc/*/stat` scan of all 1820 | 19 ms |
| | environment, arguments, folder and fd 0 of all 101 | 1.7 ms |
| Mac: 540 processes | `ps` list | 42 ms |
| | one `ps eww` | 4.3 ms each |

**Today, on a Mac with 100 sessions:**

- `live()` spawns about 3 `ps` per Claude (environment, tty, and an argument fallback): about 300 spawns, about
  1.3 s.
- `running_sids()` reads every environment again: about 0.4 s.
- Revive repeats `running_sids()` before each start, so 100 starts make about 10,000 spawns, about 43 s.
  `holder_text()` adds more.

**With this design:**

- One list read per pass. Facts are kept per (pid, start time) within the pass, and revive's check before each
  start reads only the list and any new candidates.
- **Linux:** about 25 ms per pass, whatever the count.
- **Mac:** no spawns (one `sysctl` list plus one `KERN_PROCARGS2` per candidate); expected under 50 ms for 100.
  This is to be measured on a Mac before the code is called done.
- **The record:** grows by 4 fields per row, about 100 bytes.
- **Unchanged:** one session file read per candidate, and the conversation reads that only `record` does.

## 6. Tests, written before the code

- **T56:** the late-named stand-in (`tests/fake_claude.py` through its own `/usr/bin/env` shebang), in both
  phases and in the gap.
- **A reused pid:** a pid with a stale session file is not counted as that session.
- **T57** (section 4, as rewritten):
  - the environment read made to fail for one pass: the account is kept, with one log line and no blank;
  - its owner starts a session again on another login: the row follows, with a log line and a census line, and
    the next revive starts it that way;
  - a session Tardigrade started comes up on another login: the row keeps what it had and census names it;
    `record --accept` takes what runs, for that session only.
- **T54:** one session file unreadable: its row is kept and the rest is written.
- **One folder, K=1 and N=3:**
  - All 3 sessions are held.
  - When the candidate names itself mid-wait, every session starts except the one it holds.
  - When it is still unidentified at `retry_min`, all 3 are "not started", with one log line.
  - While they are held, census and each round's log line name the process, since when, and "answer or end
    that session".
  - A new conversation with its arguments intact holds nothing back.
  - `--continue` names the latest conversation.
- **A holder from an earlier boot:** the same pid and start time under another boot id do not match.
- **An old row without `env_read`:** it adopts the facts, with one log line.
- **The Mac fallback:** the `sysctl` read is made to fail, and the run goes through the checked `ps`.
- **Case a:** an unidentified candidate in a folder that is about to be started: that one session is held and
  the rest are started.
- **T47's promise:** before the tag, census from the old build and the new build is compared on every test box.
  Both must name the same live sessions. On a Mac test box, the `sysctl` and `ps` lists are also compared
  for this user's Claude processes, and must give the same pids.

## 7. After Claude Code's own `plugin uninstall` (a decision, with its reason)

**Seen:** Claude Code's own `claude plugin uninstall` empties the plugin's row in its registry and leaves the
plugin's cache folder, marked `.orphaned_at`. It does not call this tool's `uninstall`. The boot service and the
5-minute record timer run the copy that setup made in `~/.local/share/windstorm-tardigrade/`, never the plugin's
folder, so after that uninstall both go on.

**Decision (the department head):** the boot service and the record timer go on until the person runs this
tool's own `uninstall`. They do not stop because the plugin is gone.

**Why:** a helper that types into running sessions every few minutes must stop when its plugin goes. A service
that is itself the thing the person set up is different. Bringing their sessions back after a restart is the one
promise, and a restart is the one moment it matters. A false "gone" breaks it exactly then, and at that moment
nothing is running that could be disturbed.

**What changes:** when Claude Code's registry reads fine and has no row for this plugin, every boot report, the
census and the log say so in one line: the plugin was removed by Claude Code, sessions are still brought back,
and the one command that takes it off (`python3 -I ~/.local/share/windstorm-tardigrade/tardigrade.py
uninstall`). A registry that could not be read is "cannot tell", not "removed", and changes nothing.
Only a copy that setup made from the plugin's own folder can say this. Setup writes down where it was run
from; a copy set up from a clone of the repository never had a row, so for it a missing row says nothing.
Where setup ran from has three answers too: if it could not be read, the line is not said.

**Tests, before the code:**
- a registry with no row for this plugin: the line appears in the boot report, census and log, and the start
  goes ahead;
- a registry with the row: no line;
- a copy set up from a clone, with a registry that has no row: no line;
- a copy whose recorded origin cannot be read, with a registry that has no row: no line;
- an unreadable or missing registry file: no "removed" line and no change, and the log says the registry
  could not be read.

**Argue with it here:** if a case is found where going on after Claude Code's uninstall harms the person, it
goes on this page before the code changes.

## 8. The permission mode word (T70): a note, not decided

0.1.10 changes only the words: census and the dry run say the flags a session was started with, and never name a
mode they did not read. Whether Tardigrade should ever read the mode Claude Code really runs a conversation in is
open. The only place it was seen is the conversation file's own mode field. Reading it costs opening a file the
tool otherwise leaves alone (the conversation, which holds message text), for every session, on every record.
Against that: a person sees the real mode on their own screen already. Not decided; argue it here before any code.

## Answers (the reviewer; the department head agrees on 1 and 2)

1. **Account mismatch:** first answered "hold the session"; changed on 2026-11-24, see section 4: a person's
   own restart on another login IS a person's word, so the row follows it; only a session Tardigrade itself
   started keeps its row's login when it shows another. `record --accept <session>` and `env_read` stay.
2. **An unidentified candidate:** one `retry_min` (25 min), with no new setting (P4). Census names the
   candidate at once.
3. **On a Mac:** `sysctl` through ctypes, with `ps` as the checked fallback. Before the tag: a test of the
   fallback, and the two lists compared on a Mac test box. The department head asked for the Mac read to be
   measured on a Mac first; that measurement is part of this.

Also: the boot id is part of `holder`. Asked by the department head: several sessions in one folder
(section 2, sign 4, and section 3, case a). The reviewer's ruling: hold all N sessions while any candidate there is unidentified.

## 9. Checking an upgrade on one record (open note, T71)

Seen 2026-11-23 on a shared Linux machine where a helper restarts an idle session in place every two minutes: a dry run
before setup and one after it read two different records, and a session that restarted in between (its arguments
reordered, `--allow-dangerously-skip-permissions` written out) made a start line differ, although both versions read
flags with the same code. Given the same record, both versions printed the same start lines.

Decided for 0.1.10 (T71): the dry run's header names the record it read (path, time written, short sha256); the README's
upgrade advice says to run both versions' dry runs on the same record, the old one from its kept copy by its path,
before and after setup.

Open, not decided: a `--compare-with <other script>` mode that runs both versions on one record itself and prints only
the differing lines. Its cost: a second script path on the command line that the tool runs, which setup and the boot
service never need.
